# 业务影响分析与根因定位监控系统 — 需求文档

## 1. 背景与目标

现有工具仅统计监控项覆盖率，无法支撑线上故障的快速响应。本系统面向运维一线人员，
在故障发生时回答三个问题：**出了什么问题、影响哪些业务、根因在哪里**，并给出
应急处置建议。

### 1.1 核心目标（1-15-30）

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 发现（MTTD） | ≤ 1 分钟 | 从异常发生到产生告警并推送到一线 |
| 定位（MTTL） | ≤ 15 分钟 | 从告警到锁定根因组件/变更 |
| 解决（MTTR） | ≤ 30 分钟 | 从告警到业务恢复（含应急处置） |

### 1.2 设计原则

- **业务视角优先**：一线人员先看到"业务受损程度"，再下钻到技术细节。
- **少即是多**：默认界面只呈现当前需要处置的故障，不堆砌全部指标。
- **结论先行**：系统给出可执行结论（疑似根因 + 处置建议），而非只给原始数据。
- **可解释**：每个根因判断都附带支撑证据，供人工确认，不做黑盒决策。
- **不重复造轮子**：复用现有监控工具与 ES，本系统定位为"关联分析与决策层"，
  不替代底层采集与存储。
- **先链路、后下钻**：海量对象下不靠"逐台看"，先沿交易链路把范围收敛到
  某一段应用系统，再纵向逐层下钻，保证定位路径短、可控。
- **为规模而设计**：几十万级对象常态，拓扑/链路/影响面均预聚合、增量计算，
  界面分级加载、异常优先、同类折叠。

### 1.3 技术现状与系统约束

本系统建设在既有监控体系之上，需对接以下现状：

| 维度 | 现状 |
| --- | --- |
| 应用监控 | 自研应用监控工具采集（指标 + 调用链 + 应用日志） |
| 系统监控 | 采购的系统监控工具采集基础设施指标与事件 |
| 网络监控 | 独立监控系统，告警整合接入统一平台 |
| 动环监控 | 独立监控系统，告警整合接入统一平台 |
| 数据存储 | 指标与日志统一存储在 Elasticsearch（ES）集群 |
| 配置基准 | CMDB 为唯一配置基准，各监控系统对象均与 CMDB 对齐 |
| 应用规模 | 约 400+ 套应用，主体为腾讯 TSF 框架微服务 |
| 基础设施 | 操作系统、TDSQL、GaussDB、TBDS、CRedis、网络、硬件、外设、动环 |

关键约束与设计取向：

- **ES 作为统一数据底座**：本系统优先通过 ES 查询/聚合获取指标与日志，
  不新建一套采集链路；对各监控系统的告警/事件做标准化接入。
- **CMDB 为配置基准、物理子系统为关联键**：自研工具、采购工具、网络与动环
  监控系统的对象均以 CMDB 为准对齐，并通过 **物理子系统** 维度建立跨系统关联，
  使应用、主机、数据库、网络、动环告警能归并到同一物理子系统下做影响分析。
- **告警统一接入**：网络、动环为独立监控系统，本平台不替代其采集，仅
  标准化接入其告警事件，纳入统一的故障收敛、定级与展示。
- **面向 TSF 微服务**：拓扑发现、调用链、实例维度均需适配 TSF 的
  服务/实例/部署组模型，并对接其注册中心与服务治理数据。
- **链路 + 分层双维度定位**：先沿交易链路把范围收敛到某段应用系统，
  再沿"业务 → 应用系统 → TSF 微服务 → 服务实例 → 基础设施
  （负载/数据库/MQ/存储/OS/网络/硬件/动环）"逐层下钻定位。

## 2. 用户角色

| 角色 | 关注点 | 主要场景 |
| --- | --- | --- |
| 运维一线（值班） | 现在有没有事、严不严重、我该做什么 | 故障大盘、应急处置 |
| 运维专家/SRE | 根因细节、历史趋势、误报治理 | 根因下钻、规则调优 |
| 业务/管理者 | 业务影响范围与时长 | 影响概览、复盘报告 |
| 系统管理员 | 接入配置、权限、数据源 | 配置管理 |

## 3. 功能需求

### 3.1 故障发现与告警（支撑"1 分钟发现"）

- **FR-1.1 多源数据接入**：
  - 指标与日志统一从 **ES** 查询接入，按需建立索引模板与查询适配层；
  - 接入**自研应用监控工具**的指标、调用链、应用日志；
  - 接入**采购系统监控工具**的基础设施指标与告警事件；
  - 接入**网络监控系统**与**动环监控系统**的告警事件；
  - 接入事件类数据：TSF 发布/配置变更、扩缩容、工单；
  - 所有接入对象以 **CMDB** 为基准对齐，并标注其**物理子系统**，
    使跨系统对象（主机、数据库、网络设备、动环对象）可归并关联。
- **FR-1.2 异常检测**：支持静态阈值、同比/环比、动态基线三种检测方式；
  关键业务指标检测周期 ≤ 30 秒；对 ES 中的 error/异常日志支持基于
  关键字、日志模板（pattern）与突增速率的检测。
- **FR-1.3 告警收敛**：对同一故障的多条告警按**物理子系统**、业务、拓扑维度
  聚合为单一"故障事件"——跨系统（应用/系统/网络/动环）属于同一物理子系统的
  告警可归并到同一事件；避免告警风暴，要求聚合后噪声率下降 ≥ 80%。
- **FR-1.4 分级与推送**：按业务影响自动定级（P1-P4），通过站内、短信、IM、电话
  分级触达；P1 推送延迟 ≤ 1 分钟。
- **FR-1.5 告警闭环**：每条故障事件具备状态机（新建 → 已认领 → 处置中 → 已恢复 →
  已复盘），全程留痕。

### 3.2 业务影响分析（回答"影响什么业务"）

- **FR-2.1 分层拓扑（纵向六层）**：维护并自动发现以下分层依赖拓扑——
  1. **业务层**：几十类业务/交易；
  2. **应用系统层**：400+ 应用系统；
  3. **微服务层**：TSF 微服务（从注册中心/调用链自动发现服务及其依赖）；
  4. **实例层**：TSF 服务实例 / 部署组 / 容器 / 服务器（单系统可达数千台）；
  5. **基础设施层**：负载（LB）、TDSQL、GaussDB、TBDS、CRedis、MQ、存储、
     操作系统、网络设备、硬件、外设；
  6. **环境层**：动环（机房动力与环境）。
  纵向拓扑表达"谁依赖谁"，用于影响面上钻与根因下钻。
- **FR-2.2 链路模型（横向三级）**：在分层拓扑之上维护交易的实际流转链路——
  1. **交易链路**：一笔交易跨多个应用系统的端到端流转（如 下单 → 风控 →
     支付 → 账务），标注每段所属系统、调用顺序与关键节点；
  2. **微服务链路**：应用系统内部 TSF 微服务调用链（基于调用链/Trace 发现）；
  3. **资源访问链路**：微服务到所依赖资源的访问路径——负载、数据库、MQ、
     存储等，每类资源链路可单独呈现与排障。
  链路模型表达"交易怎么走"，用于沿真实路径定位是哪一段、哪一跳出问题。
- **FR-2.3 链路数据源融合（人工梳理链路 + 链路追踪）**：交易链路来自两类
  数据，需在平台内桥接互补——
  1. **人工梳理的系统链路**为骨架：带业务含义（属于哪类业务、哪类交易），
     定义交易应经过的系统及顺序；平台需支持其录入、版本管理与负责人维护。
  2. **单笔链路追踪（Trace）**为运行时明细：覆盖真实调用路径与各跳耗时/状态，
     但**只含 URL 与接口信息，无交易码/产品码/渠道等业务标识**。
  3. **Trace 业务打标（基于入口接口映射表）**：因 Trace 无业务标识，打标以
     **"入口 URL/接口 → 业务交易类型"映射表**为主要手段——
     - 映射表由人工维护，并与人工梳理链路的入口节点对齐；
     - 支持按 URL 路径前缀/通配、接口名精确匹配等规则；
     - 平台辅助治理：自动列出未命中映射表的高频入口接口，提示补录，
       降低人工维护成本；
     - 同一入口对应多种交易时，需结合可识别的 URL 参数细分（能力有限时
       归并为粗粒度交易类型，不强求单笔精确）。
  4. **链路绑定与对账**：将打标后的 Trace 实际路径与人工梳理链路比对，
     一致则用 Trace 丰富链路明细与实时健康度；不一致则告警提示
     "实际路径与梳理链路偏差"，供人工校正梳理结果。
  入口接口映射表与梳理链路均可配置维护，平台优先用 Trace 校验和补全人工链路。
- **FR-2.4 拓扑自动发现与规模治理**：分层拓扑与微服务/资源链路以自动发现
  为主、人工校正为辅；交易链路以人工梳理为基准、Trace 校验补全；
  面对几十万级对象，拓扑/链路需增量更新与预聚合，界面按业务/系统/链路
  分级加载，默认不渲染单机级全量节点，按需下钻。
- **FR-2.5 影响面计算**：故障发生时，自动沿纵向拓扑上钻并沿交易链路扩散，
  列出受影响的业务、应用系统、交易链路，预估受影响交易量/用户数。
- **FR-2.6 业务健康度**：每类业务、每条交易链路用统一健康分（成功率、时延、
  流量综合）表达，红/黄/绿三态，一线无需理解底层指标即可判断严重性。
- **FR-2.7 影响时间线**：以时间轴呈现"指标恶化 → 告警 → 业务跌量 → 恢复"过程，
  量化业务损失（受损时长、损失交易量）。

### 3.3 根因定位（支撑"15 分钟定位"）

- **FR-3.1 链路定位（先定位到段）**：故障发生时先在**交易链路**上定位是哪一段
  应用系统异常，再进入该系统沿**微服务链路**定位异常微服务，再沿**资源访问链路**
  判断是负载、数据库、MQ 还是存储问题——先横向收敛范围，再纵向下钻。
- **FR-3.2 逐层下钻定位**：锁定异常对象后沿六层拓扑一键逐层下钻——业务 →
  应用系统 → TSF 微服务 → 服务实例 → 基础设施（负载/TDSQL/GaussDB/TBDS/
  CRedis/MQ/存储/OS/网络/硬件/外设）→ 动环；每一层只展示该层异常对象并标注
  异常证据（指标、日志、事件），下钻路径默认自动收敛到异常子树，
  一线人员沿红色路径点到底即可。海量实例下采用"异常优先、聚合展示"，
  同类正常实例折叠，不逐台铺开。
- **FR-3.3 资源链路专项视图**：针对负载、TDSQL、GaussDB、TBDS、CRedis、MQ、
  存储分别提供专项排查视图（如 LB 后端摘除、慢 SQL/锁等待、连接数、主从延迟、
  缓存命中率/大 key、消息积压、存储 IO/容量），下钻到具体实例时直接呈现
  该类组件的关键指标。
- **FR-3.4 错误日志快速排查（核心）**：下钻到任意异常对象时，一键拉取该对象
  在故障时间窗内的 error/异常日志，详见 3.4 节。
- **FR-3.5 变更与事件关联**：自动关联故障时间窗内的 TSF 发布、配置变更、
  扩缩容、工单，以及网络/动环告警事件，按时间相关性排序
  （变更是最常见根因，需优先呈现）。
- **FR-3.6 根因候选排序**：综合链路异常传播方向、指标相关性、错误日志聚类、
  变更关联、历史相似故障，输出 Top-N 疑似根因，每项给出置信度与支撑证据，
  并标注根因所在交易链路段与层级（应用 / 数据库 / MQ / 存储 / 网络 / 硬件 /
  动环）。
- **FR-3.7 关联分析**：支持指标 / 日志 / 调用链三态联动——选定时间点可同时
  查看对应的错误日志样本与慢调用链。
- **FR-3.8 相似故障检索**：基于故障特征检索历史相似事件，复用其根因与处置过程。

### 3.4 错误日志快速排查（基于 ES）

针对"快速排查日志里的 error 和报错"的核心诉求，专设此模块：

- **FR-LOG-1 上下文直达**：从任意故障/异常对象（业务、微服务、实例、数据库）
  一键跳转到其错误日志视图，自动带入对象标识与故障时间窗，无需手工写 ES 查询。
- **FR-LOG-2 错误日志聚合**：对 ES 中的 error/exception 日志做模板聚类
  （按异常堆栈/日志模板归并），呈现"错误类型 + 出现次数 + 首次/末次时间 +
  影响实例数"，避免一线在海量日志中逐条翻找。
- **FR-LOG-3 突变识别**：自动标出故障窗内**新出现**或**突增**的错误类型，
  并与历史基线对比，优先把"新错误"推到最前——这通常最接近根因。
- **FR-LOG-4 错误下钻**：点击某错误类型可查看原始日志样本、完整异常堆栈、
  按实例/时间的分布；支持关联同 traceId 的上下游调用链与日志。
- **FR-LOG-5 快速检索**：提供关键字、日志级别、服务/实例、时间范围的简易
  检索面板（封装 ES 查询），并支持保存常用查询。
- **FR-LOG-6 错误结论**：在故障详情页给出错误日志摘要结论，
  如"实例 X 在 14:03 起出现 N 次 `SQLException: connection timeout`，
  指向 TDSQL 连接异常"。
- **FR-LOG-7 已知错误库**：可将常见错误模式登记为"已知错误"并关联处置预案，
  再次出现时直接给出结论与建议。

### 3.5 应急处置建议（支撑"30 分钟解决"）

- **FR-4.1 处置预案库**：按故障类型/组件维护可检索的处置预案（SOP），
  每个预案关联可执行的处置动作，支持手工维护与从历史复盘沉淀。
- **FR-4.2 智能推荐**：根据疑似根因匹配并推荐处置动作（如回滚 TSF 发布、
  重启实例、限流降级、扩容、切流、切主备），并标注预期效果与风险等级。
- **FR-4.3 一键处置执行**：推荐的处置动作在故障详情页以**可点击按钮**呈现，
  一线人员确认后直接在平台触发执行，无需切换到其他系统。
  - 对接执行通道：TSF（重启/回滚/扩缩容）、脚本/作业平台、数据库切换等；
  - 执行前展示动作说明、影响范围、风险等级，并做二次确认与权限（RBAC）校验；
  - 高风险动作需审批；执行过程与结果全程审计留痕。
- **FR-4.4 处置效果反馈**：执行动作后持续观测健康度，确认是否恢复，
  未恢复则提示尝试下一候选方案；支持一键回退已执行动作。

### 3.6 一线运维界面（简洁、直观）

- **FR-5.1 故障大盘（首页）**：默认只展示"当前进行中故障"卡片，按 P 级排序；
  每张卡片一屏内呈现：业务名、影响概述、严重级别、持续时长、疑似根因、
  建议动作、认领按钮。无故障时显示全绿状态。
- **FR-5.2 故障详情页（三段式）**：上=业务影响摘要，中=逐层下钻的根因定位路径
  与证据（含错误日志聚合面板），下=处置建议与可一键执行的操作按钮、操作记录；
  一线人员从上往下读即可完成处置。
- **FR-5.3 一句话结论**：每个故障在顶部用一句自然语言概括
  （如"支付网关因 14:02 的配置发布导致响应时间上升，建议回滚"）。
- **FR-5.4 双形态部署（Web + 移动端）**：
  - **Web 端**：完整功能，面向值班、SRE、管理者，含大盘、下钻、日志排查、
    处置执行、复盘；
  - **移动端**：面向值班随身场景，支持故障推送接收、查看影响与根因结论、
    认领、一键处置（按权限）、协同;两端账号、权限与数据一致。
- **FR-5.5 协同**：故障详情页内置处置时间线/讨论区，支持 @人、记录关键操作。

### 3.7 复盘与持续改进

- **FR-6.1 自动复盘报告**：故障恢复后自动生成报告草稿（时间线、影响、根因、
  处置、MTTD/MTTL/MTTR）。
- **FR-6.2 指标看板**：统计 1-15-30 达标率、误报率、告警收敛率、预案命中率，
  按周/月趋势呈现。
- **FR-6.3 知识沉淀**：复盘结论可一键回写到预案库与相似故障库。

## 4. 非功能需求

## 5. 关键数据模型（概念）

- **物理子系统（PhysicalSubsystem）**：CMDB 中的物理子系统，作为跨监控系统
  对象关联与告警归并的核心维度。
- **业务（Business）**：几十类业务之一，含业务名、负责人、SLO、关联交易链路。
- **应用系统（AppSystem）**：400+ 应用系统之一，含所属业务、包含的微服务。
- **微服务（Microservice）**：TSF 服务名、所属应用系统、部署组、上下游依赖。
- **服务实例（Instance）**：所属微服务、部署组、IP/容器、承载主机。
- **基础设施对象（Infra）**：类型（负载/TDSQL/GaussDB/TBDS/CRedis/MQ/存储/
  OS/网络/硬件/外设/动环）、标识、所属物理子系统、承载的实例、来源监控系统。
- **CMDB 配置项（CI）**：所有对象的配置基准，含物理子系统归属关系。
- **交易链路（TransactionChain）**：一类交易的端到端路径，由有序链路段组成；
  含业务含义（所属业务、交易类型）、来源（人工梳理）、版本、负责人。
- **链路段（ChainSegment）**：链路中的一段，标注所属应用系统、调用顺序、
  上下游、内部微服务链路与资源访问链路引用。
- **链路（Link）**：通用调用/依赖关系，类型为微服务链路或资源访问链路
  （负载/数据库/MQ/存储），用于沿真实路径定位。
- **链路追踪（Trace）**：单笔交易运行时调用明细，含 traceId、各跳服务/耗时/
  状态、入口 URL 与接口（无业务标识）；经打标后关联到交易链路。
- **入口接口映射表（EntryApiMapping）**：入口 URL/接口 → 业务交易类型的
  人工维护映射，支持路径前缀/通配/精确匹配，是 Trace 业务打标的主要依据。
- **链路对账记录（ChainReconciliation）**：Trace 实际路径与人工梳理链路的
  比对结果，记录一致性与偏差点，供人工校正。
- **监控指标（Metric）**：归属对象、来源工具、ES 索引、检测规则、基线。
- **日志/错误（LogEntry / ErrorPattern）**：归属对象、级别、日志模板、
  ES 索引、堆栈、traceId；ErrorPattern 记录错误模板与是否已知错误。
- **故障事件（Incident）**：级别、状态、影响业务与交易链路、所属物理子系统、
  时间线、根因（含链路段与层级）、处置记录、MTTD/MTTL/MTTR。
- **变更（Change）**：类型（TSF 发布/配置/扩缩容/工单）、对象、时间、
  操作人，用于根因关联。
- **处置预案（Runbook）**：适用故障类型、步骤、风险等级、预期效果。
- **处置动作（RemediationAction）**：动作类型、执行通道（TSF/作业平台/数据库等）、
  参数、风险等级、所需权限、是否需审批、执行与回退记录。
- **对象映射（ObjectMapping）**：各监控系统对象与 CMDB 配置项的归一化映射。

## 6. 验收标准

1. 注入一个典型故障（如某次错误发布），系统在 1 分钟内产生 P1 告警并推送。
2. 故障大盘首页一屏内可看清"哪个业务受影响、严重程度、疑似根因"。
3. 单笔 Trace 可按入口接口映射表打标到业务交易类型，并绑定到人工梳理的交易链路；
   未命中映射的高频入口接口能被自动列出以提示补录。
4. 跨多个应用系统的交易故障，可在交易链路上定位到具体异常的链路段（系统）。
6. 进入异常系统后可沿微服务链路与资源访问链路定位到负载/数据库/MQ/存储某一跳。
7. 可逐层下钻至 TSF 微服务、实例、基础设施对象，路径每跳有异常证据。
8. 一键拉取异常对象的 ES 错误日志，聚合呈现错误类型并标出故障窗内的新增错误。
9. 同一物理子系统下应用、系统、网络、动环的多条告警能收敛为一个故障事件。
10. 根因候选 Top-3 中包含真实根因，且关联出对应变更。
11. 处置建议以可点击按钮呈现，确认后在平台内直接触发执行并全程审计。
12. 处置动作执行后健康度恢复并自动确认；未恢复时提示下一候选方案。
13. 移动端可接收故障推送、查看根因结论并按权限执行一键处置。
14. 故障恢复后自动生成含 MTTD/MTTL/MTTR 的复盘报告草稿。
15. 在数十万级对象规模下，故障详情页与逐层下钻仍满足性能指标。
16. 连续运行下告警误报率 ≤ 5%，告警收敛率 ≥ 80%。

## 7. 分期规划（建议）

| 阶段 | 范围 | 目标 |
| --- | --- | --- |
| 一期 | 各监控系统与 ES 接入、CMDB 对齐与物理子系统关联、六层分层拓扑自动发现、异常检测、告警收敛、故障大盘、影响面、Web 端 | 打通"1 分钟发现 + 看清影响" |
| 二期 | 人工梳理链路录入、Trace 业务打标与链路对账、微服务/资源链路建模、链路定位、逐层下钻、错误日志快速排查、资源链路专项视图、变更关联、根因候选排序、三态联动、移动端 | 实现"15 分钟定位" |
| 三期 | 预案库、智能推荐、一键处置执行与回退、已知错误库、自动复盘与指标看板、大规模性能优化 | 实现"30 分钟解决"与持续改进 |

## 8. 范围之外（本期不做）

- 不替代专业 APM/日志平台的全量存储与检索，仅做接入与关联。
- 不替代网络、动环监控系统的采集，仅整合其告警。
- 不做业务系统的自动容量规划。
- 一键处置覆盖标准化运维动作；高风险动作需平台内审批，非标变更仍走标准变更流程。
